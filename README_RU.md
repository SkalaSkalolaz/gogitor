# Gogitor — AI-ассистент программиста для Go

[![License](https://img.shields.io/badge/License-BSD--3--Clause-blue.svg)](LICENSE.txt)
[![Go](https://img.shields.io/badge/Go-1.25.1-00ADD8.svg)](https://go.dev/)

[![Platform](https://img.shields.io/badge/platform-Linux%20%7C%20macOS%20%7C%20WSL-lightgrey.svg)](#требования)

[English version](README.md)

**Gogitor** — интеллектуальный терминальный ассистент программиста для разработки на Go.

Он объединяет классический CLI, интерактивный терминальный интерфейс, генерацию и анализ кода с учётом проекта, автоматическую проверку изменений, multi-agent оркестрацию, Git/GitHub, веб-поиск, индексирование проекта и сохранение инженерного контекста между сессиями.

Gogitor может работать как с **локальными LLM через Ollama**, так и с **OpenAI-совместимыми API**. Ассистент способен понять задачу на естественном языке, изучить существующий проект, сформировать изменения, проверить их в изолированной временной рабочей области, запустить сборку и тесты и только после успешной проверки применить изменения к реальному проекту.

Для сложных задач Gogitor может использовать конвейер из нескольких специализированных агентов: планирование, реализация, ревью и финальная проверка.

> **Текущая версия:** `0.9.0`

> Gogitor ориентирован прежде всего на проекты на Go. Интерфейс программы поддерживает русский и английский языки.

# Что такое Gogitor

Gogitor задуман как промежуточный слой между разработчиком и большой языковой моделью.

Вместо простого отправления промпта модели и копирования полученного кода обратно в проект Gogitor организует вокруг LLM полноценный инженерный процесс:

```text
Задача пользователя
        │
        ▼
Определение намерения
        │
        ├── Chat
        ├── Анализ
        ├── Web Search
        ├── Генерация кода
        ├── Исправление
        ├── Запуск
        ├── Тестирование
        ├── Git
        └── Article
             │
             ▼
Контекст проекта / AST-индекс
             │
             ▼
            LLM
             │
             ▼
      Файлы / патчи
             │
             ▼
    Временная sandbox-среда
             │
             ├── go mod init
             ├── go mod tidy
             ├── gofmt
             ├── go build
             ├── go test
             ├── go vet
             └── golangci-lint
             │
             ▼
      Проверенный результат
             │
             ├── Применение изменений
             └── Git commit
```

Для сложных задач этот процесс может расширяться до нескольких специализированных агентов и полноценного Workflow с сохраняемыми артефактами.

# Возможности

## Интерактивный TUI

Gogitor предоставляет интерактивный терминальный интерфейс на базе **Bubble Tea**.

TUI поддерживает:

* отображение Markdown;
* историю диалога;
* автодополнение команд;
* потоковую выдачу ответа LLM;
* переключение фокуса между элементами интерфейса;
* выделение текста мышью;
* отображение процесса выполнения операций;
* план выполнения multi-agent задач;
* отображение статуса задач;
* оценку времени выполнения;
* диагностику проекта и LLM;
* русский и английский интерфейс.

Запуск:

```bash
./gogitor
```

или:

```bash
./gogitor tui
```

# Генерация кода

Gogitor умеет создавать новый Go-код и изменять существующий проект с учётом его текущей структуры.

Поддерживаются:

* создание новых файлов;
* изменение существующих файлов;
* рефакторинг;
* разделение кода между файлами;
* выделение функций и компонентов;
* исправление ошибок компиляции;
* исправление неудачных тестов;
* реализация новых функций;
* выполнение задач из `.txt` и `.md` файлов;
* применение минимальных патчей;
* генерация полного файла, когда применение патча невозможно.

## Patch Mode

Для существующего кода Gogitor может использовать минимальные `SEARCH/REPLACE`-патчи:

```text
--- Patch: path/to/file.go ---
<<<<<<< SEARCH
точный существующий код
=======
новый код
>>>>>>> REPLACE
```

Блок `SEARCH` должен соответствовать исходному файлу с учётом отступов и окружающего контекста.

Если патч невозможно безопасно применить или его применение приводит к ошибке, Gogitor может автоматически перейти к генерации полного файла.

# Проверка и исправление ошибок

Сгенерированные изменения не должны сразу попадать в рабочий проект.

Сначала Gogitor работает с временной копией проекта и выполняет проверки.

В зависимости от операции могут запускаться:

```text
go mod init
go mod tidy
gofmt
go build
go test -v -cover
go vet
golangci-lint
```

Результаты тестирования анализируются автоматически.

Gogitor может извлекать:

* успешно выполненные тесты;
* неудачные тесты;
* имена тестов;
* функции;
* исходные файлы;
* номера строк;
* сообщения об ошибках;
* информацию о покрытии.

Эта информация может передаваться обратно LLM для формирования точечного исправления.

## Исправление ошибок

Команда `fix` предназначена для исправления:

* ошибок компиляции;
* падений программы;
* panic;
* stack trace;
* ошибок тестов.

Например:

```bash
./gogitor fix "panic: runtime error: index out of range [3] with length 2"
```

Gogitor также умеет распознавать характерные признаки Go-ошибок:

```text
panic:
runtime error
goroutine
.go:123
--- FAIL
```

и автоматически выбирать соответствующий режим исправления.

# Multi-Agent разработка

Для сложных задач Gogitor может использовать несколько специализированных агентов:

```text
┌──────────┐
│ Planner  │
└────┬─────┘
     │
     ▼
┌──────────┐
│  Coder   │
└────┬─────┘
     │
     ▼
┌──────────┐
│ Reviewer │
└────┬─────┘
     │
     ▼
┌──────────┐
│ Verifier │
└──────────┘
```

## Planner

Разбивает сложную задачу на несколько конкретных подзадач и формирует критерии их принятия.

## Coder

Реализует подзадачи и проверяет полученный проект.

## Reviewer

Проверяет изменения на наличие существенных проблем:

* ошибок компиляции;
* неправильной реализации;
* потенциальных nil dereference;
* проблем безопасности;
* регрессий;
* несоответствия исходной задаче.

## Verifier

Проверяет, была ли исходная задача действительно выполнена.

Если результат неудовлетворителен, агент может сформировать дополнительную задачу на исправление.

Multi-agent система также поддерживает:

* единую очередь запросов к LLM;
* приоритеты;
* бюджеты для ролей;
* автоматические повторные попытки;
* exponential backoff;
* статистику использования LLM;
* оценку времени выполнения;
* persistent agent memory;
* checkpoint и rollback.

# Workflow Mode

Workflow Mode предназначен для крупных инженерных задач, где важны последовательность действий, проверяемость и трассируемость.

Запуск:

```bash
./gogitor workflow "создать REST API с авторизацией и тестами"
```

Для каждой сессии создаётся отдельная директория:

```text
.gogitor/workflow/<timestamp>/
```

В ней сохраняются артефакты:

```text
inbox.md
research.md
plan.md
prd.json
process.md
gate-report-task-01.json
gate-report-task-02.json
...
```

Workflow:

1. Уточняет исходную цель.
2. Разбивает задачу на 2–5 атомарных подзадач.
3. Выполняет каждую подзадачу через Coder Agent.
4. После каждой задачи запускает Quality Gates.
5. Сохраняет информацию о выполнении.
6. При включённом автоматическом Git commit создаёт отдельный commit для задачи.
7. Останавливается, если обязательная проверка не пройдена.

## Quality Gates

После каждой задачи выполняются:

```text
go build
go test
go vet
gofmt -l
golangci-lint
```

Если все проверки пройдены, задача считается успешно завершённой.

Если хотя бы одна обязательная проверка завершается ошибкой, Workflow останавливается.

# Workflow Interview

Для неоднозначных задач можно использовать предварительное интервью:

```bash
./gogitor workflow interview "добавить кэширование в API layer"
```

Planner Agent формирует 3–5 уточняющих вопросов с предлагаемыми значениями по умолчанию.

Ответы можно вводить в формате:

```text
1: использовать in-memory cache
2: кэшировать только GET
3: очищать кэш после записи
```

Также можно ввести:

```text
skip
```

или:

```text
go
```

чтобы принять все предложенные значения по умолчанию.

После этого Gogitor формирует уточнённую задачу и запускает обычный Workflow.

Интервью особенно полезно, когда исходное описание задачи недостаточно конкретно.

---

# Workflow Reflection

После завершения Workflow можно выполнить ретроспективный анализ:

```bash
./gogitor workflow reflect
```

Gogitor находит последнюю Workflow-сессию и анализирует её артефакты:

```text
inbox.md
process.md
prd.json
gate-report-task-*.json
```

Результат сохраняется в:

```text
reflection.md
```

Рефлексия содержит:

* что прошло хорошо;
* что можно улучшить;
* сводку метрик;
* рекомендации;
* итоговый вердикт.

Для небольших локальных моделей используется упрощённый промпт.

# Workflow Pull Request

После завершения Workflow можно автоматически создать Pull Request:

```bash
./gogitor workflow pr
```

Для этого требуется:

* Git-репозиторий;
* настроенный remote `origin`;
* GitHub token через `--key-github` или `GOGITOR_GITHUB_TOKEN`.

Gogitor анализирует артефакты последней Workflow-сессии и формирует структурированное описание PR, включающее:

* исходную цель;
* план реализации;
* таблицу задач;
* статусы и commit;
* результаты Quality Gates;
* последние строки журнала выполнения;
* рефлексию, если она была создана.

Затем Gogitor:

1. определяет подходящую ветку;
2. создаёт `workflow/<slug>`, если работа выполняется непосредственно в `main`/`master`;
3. либо переиспользует существующую feature/workflow-ветку;
4. отправляет ветку в `origin`;
5. создаёт Pull Request через GitHub API.

# Интеллектуальный анализ проекта

Gogitor не отправляет в LLM все файлы проекта без разбора.

Вместо этого он поддерживает AST-based индекс проекта и использует его для выбора наиболее релевантного контекста.

Индекс учитывает:

* Go-файлы;
* пакеты;
* импорты;
* функции;
* методы;
* связи вызовов;
* структуру проекта;
* важность файлов;
* текстовую релевантность.

Для ранжирования используются:

* граф импортов;
* call graph;
* PageRank;
* BM25;
* расширение синонимов на русском и английском языках.

Это позволяет выбирать наиболее важные для текущей задачи файлы и не перегружать контекст LLM всем проектом.

# Сравнение подходов

Для достаточно сложных задач Gogitor может до начала написания кода предложить 2–3 принципиально разных варианта реализации.

Например:

```text
## Сравнение подходов

| # | Подход          | Сложность | Производительность | Читаемость | Зависимости |
|---|-----------------|-----------|--------------------|------------|-------------|
| 1 | stdlib HTTP mux | низкая    | хорошая             | отличная   | только stdlib |
| 2 | chi router      | средняя   | отличная            | хорошая    | 1 внешняя   |
| 3 | gRPC            | высокая   | отличная            | средняя    | 3 внешние   |
```

Пользователь может:

* выбрать вариант по номеру;
* написать `yes` для принятия рекомендации;
* предложить собственный вариант;
* изменить рекомендованный вариант.

Функцию можно отключить:

```bash
./gogitor code "создать HTTP сервер" --no-compare
```

или:

```bash
GOGITOR_COMPARE_APPROACHES=false
```

# Автоматическое определение типа задачи

Gogitor способен определить необходимый режим по естественно-языковому запросу.

Например:

```text
"напиши HTTP сервер"
        → code

"объясни context.Context"
        → chat

"найди ошибки в проекте"
        → analyze

"последняя версия Go"
        → search

"запусти тесты"
        → test

"сделай commit"
        → git

"исправь этот panic..."
        → fix

"напиши статью о Go"
        → article
```

Таким образом, пользователю не обязательно каждый раз явно указывать режим работы.

# Режим размышления (Reasoning)
Gogitor поддерживает режим размышления (thinking/reasoning) для моделей,
которые его поддерживают (DeepSeek-R1, QwQ, Qwen3, OpenAI o1/o3/o4-mini и др.).

Флаги командной строки:
  --reasoning            Включить режим размышления (thinking)
  --reasoning-effort <v> Глубина размышления: low, medium, high
  --reasoning-budget <n> Макс. токенов на размышление (0=по умолчанию сервера)
  --reasoning-show       Показывать процесс размышления в выводе

Команда TUI:
  :reasoning             Показать текущее состояние режима размышления
  :reasoning on          Включить режим размышления
  :reasoning off         Выключить режим размышления

Переменные окружения:
  GOGITOR_REASONING=true         Включить режим размышления
  GOGITOR_REASONING_EFFORT=high  Глубина размышления
  GOGITOR_REASONING_BUDGET=8192  Макс. токенов на размышление

Конфигурация (.gogitor.json):
  {
    "reasoning_enabled": true,
    "reasoning_effort": "high",
    "reasoning_budget": 8192,
    "reasoning_show": false
  }

Примечание:
  - Для Ollama используется параметр "think": true
  - Для OpenAI-совместимых API используется "reasoning_effort"
  - Если модель не поддерживает reasoning, параметр игнорируется
    или запрос повторяется без него (зависит от провайдера)

# Процесс генерации кода

При выполнении задачи на изменение кода Gogitor использует последовательность, ориентированную на безопасную проверку результата.

## 1. Анализ задачи

Gogitor определяет тип запроса.

Для сложных задач создаётся план и набор подзадач.

## 2. Формирование контекста

Индекс проекта используется для выбора наиболее релевантных файлов.

## 3. Генерация изменений

LLM может вернуть полные файлы:

```text
--- File: main.go ---
package main

...
```

или минимальный патч:

```text
--- Patch: internal/server/server.go ---
<<<<<<< SEARCH
старый код
=======
новый код
>>>>>>> REPLACE
```

## 4. Создание временной рабочей области

Текущий проект копируется во временную директорию.

## 5. Применение изменений

Сгенерированные файлы или патчи применяются к временной копии.

## 6. Проверка

Выполняются необходимые проверки:

```text
go mod init
go mod tidy
gofmt
go build
go test -v -cover
```

В Workflow дополнительно выполняются Quality Gates.

## 7. Применение результата

Только после успешной проверки изменения переносятся в настоящий проект.

## 8. Git

При включённом автоматическом commit Gogitor формирует сообщение на основе фактического diff и создаёт commit.

# Индексирование проекта

Индекс проекта предназначен для интеллектуального выбора контекста.

Он анализирует Go-код и строит связи:

```text
Файлы
 │
 ├── Пакеты
 │
 ├── Импорты
 │
 ├── Функции
 │
 └── Вызовы
```

## Граф импортов

Позволяет определить зависимости между файлами и пакетами.

## Call Graph

Используется для определения связей между функциями и методами.

## PageRank

Позволяет находить наиболее важные файлы проекта с точки зрения структуры зависимостей.

## BM25

Ранжирует файлы по текстовой релевантности текущей задаче.

Для русско- и англоязычных запросов используется расширение синонимов.

Индекс кешируется в каталоге пользовательского кеша и автоматически обновляется при изменении исходных файлов.

# Журнал инженерных решений

В multi-agent сессиях Gogitor может сохранять важные инженерные решения.

Журнал содержит информацию о:

* принятых решениях;
* рассмотренных альтернативах;
* ограничениях;
* причинах выбора;
* неудачных подходах.

Просмотр:

```bash
./gogitor decisions
```

Gogitor также может попросить LLM определить **decision debt** — временные инженерные решения, ограничения которых могли перестать быть актуальными.

Это помогает обнаруживать компромиссы, которые стоит пересмотреть позднее.

# Безопасность

Gogitor — инструмент разработки, который способен выполнять сгенерированный код и изменять файлы на компьютере пользователя.

Поэтому код, созданный LLM, следует считать недоверенным до тех пор, пока он не прошёл проверку.

## Рекомендуемые меры

* Используйте Git.
* Храните важные проекты под контролем версий.
* Используйте `--dry-run` при проверке незнакомых задач.
* Просматривайте изменения перед commit.
* Используйте доверенные LLM endpoint.
* Не передавайте секреты внешним моделям.
* Проверяйте task-файлы перед выполнением.
* Не считайте успешную компиляцию доказательством корректности реализации.

## Sandbox

Генерация и проверка кода выполняются во временной рабочей области.

Изменения сначала применяются к копии проекта, после чего выполняются необходимые проверки.

Только после успешной валидации изменения переносятся в реальный проект.

Sandbox предназначена для защиты рабочего дерева от непосредственного попадания сломанного сгенерированного кода.

При этом sandbox **не является полноценным контейнером безопасности или виртуальной машиной**.

Сгенерированный код всё ещё может выполнять операции, разрешённые операционной системой и текущей учётной записью.

## Защита путей

Gogitor проверяет пути файлов перед применением изменений и блокирует попытки path traversal, которые могли бы привести к записи за пределами корня проекта.

# Устранение проблем

## `unsupported provider`

Используйте один из поддерживаемых форматов:

```bash
--provider ollama
```

```bash
--provider http://localhost:11434
```

```bash
--provider openai+https://api.example.com/v1
```

```bash
--provider openai-compatible+http://localhost:8000/v1
```

---

## Ollama недоступен

Убедитесь, что Ollama запущен:

```bash
ollama serve
```

Затем:

```bash
./gogitor tui \
  --provider http://127.0.0.1:11434 \
  --model gemma3:4b
```

---

## Ошибка сборки

Сначала самостоятельно проверьте проект:

```bash
go build ./...
```

Затем снова запустите Gogitor.

Если ошибка была внесена сгенерированным кодом:

```bash
./gogitor fix "вставьте сюда ошибку сборки"
```

---

## Не проходят тесты

Запустите тесты:

```bash
./gogitor test --json
```

Для временного пропуска тестов при генерации:

```bash
./gogitor code "задача" --no-tests
```

Пропуск тестов следует рассматривать только как временный режим разработки, а не как замену полноценной валидации.

---

## `golangci-lint` не установлен

Установите:

```bash
go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest
```

После этого:

```bash
./gogitor test lint
```

---

## Недостаточный контекст модели

Для больших проектов и масштабного рефакторинга можно увеличить контекст:

```bash
./gogitor code "рефакторинг всего проекта" \
  --max-context 262144
```

или указать его в конфигурации:

```json
{
  "max_context_tokens": 262144
}
```

Фактический доступный контекст зависит от выбранной модели и LLM-провайдера.

---

## Проверка конфигурации

Используйте:

```bash
./gogitor doctor
```

Для подробных логов:

```bash
./gogitor --debug
```

# Разработка

Сборка:

```bash
go build ./...
```

Запуск тестов:

```bash
go test ./...
```

Статический анализ:

```bash
go vet ./...
```

Форматирование:

```bash
gofmt -w .
```

Lint:

```bash
golangci-lint run ./...
```

Эти же категории проверок используются Gogitor при валидации сгенерированного кода и выполнении Workflow Quality Gates.

# Участие в разработке

Предложения по улучшению, сообщения об ошибках, новые функции и Pull Request приветствуются.

При создании issue желательно указать:

* версию Gogitor;
* версию Go;
* операционную систему;
* LLM-провайдера;
* название модели;
* выполненную команду;
* текст ошибки;
* использовался ли TUI или CLI.

Перед созданием Pull Request убедитесь, что проект собирается и тесты проходят:

```bash
go build ./...
go test ./...
```

Для изменений, затрагивающих качество генерируемого кода, также рекомендуется проверить:

```bash
go vet ./...
golangci-lint run ./...
```
